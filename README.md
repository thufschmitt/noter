# Longhand for Windows

A native Windows prototype of Longhand: one endless ruled notebook page. Write with a pen. When you tap **Ask** (or press Ctrl+Enter), an OpenAI model, through your ChatGPT subscription, writes its answer in blue handwriting on the lines just below your ink, and anything further down moves to make room.

It uses Windows Ink (`InkCanvas`), so pen strokes are drawn by the system on its low-latency path, with pressure, palm rejection and the pen's eraser end built in.

## Requirements

- Windows 10 version 1809 or later, or Windows 11, with the Microsoft Edge WebView2 Runtime (it comes with Windows 11 and current Windows 10)
- Visual Studio 2022 17.14 or later, or Visual Studio 2026, with the **Universal Windows Platform tools** workload. This is UWP on modern .NET 10.
- A ChatGPT subscription, and the Codex CLI signed in with it (Longhand uses its sign-in, see below)

## Build and run

With Nix, `nix develop` gives you everything for the Linux side (.NET 10, Node, Chromium), `nix run .#web` starts the web version and `nix run .#check` runs every check that works off Windows.

1. Open `Longhand/Longhand.csproj` in Visual Studio.
2. Pick your platform (x64 or ARM64) and press F5. Visual Studio restores the NuGet packages, deploys the app and starts it.
3. Sign in to the Codex CLI with ChatGPT (`codex login`), click the gear button and paste the contents of `~/.codex/auth.json`. It's stored in Windows Credential Manager, not in any file.

If Visual Studio won't load the project file, create a new project from the **UWP Blank App** template (the .NET one), name it `Longhand`, then:
- Add the `HtmlSanitizer` and `Microsoft.UI.Xaml` NuGet packages.
- Copy `MainPage.xaml`, `MainPage.xaml.cs` and the `Services` folder into the new project.
- Add `<PublishAot>false</PublishAot>` to the new project's csproj.

## Installing and updating

Every push to `main` builds signed packages and publishes them as a GitHub Release. A small GitHub Pages site next to it holds the `.appinstaller` files that tell Windows which version is newest; they point at the packages on the Release.

One-time setup of the repository: Settings → Pages → Source: **GitHub Actions**.

One-time setup of each PC:

1. Trust the certificate, in an administrator terminal: `certutil -addstore TrustedPeople Longhand.cer`
2. Open the `.appinstaller` link for your PC (x64 or ARM64) and choose Install. They are `https://thufschmitt.github.io/noter/Longhand-x64.appinstaller` and `https://thufschmitt.github.io/noter/Longhand-arm64.appinstaller`.

After that, starting the app from the Start menu or a tile checks for a newer version first and asks to install it before the app opens. (A taskbar or desktop shortcut skips the prompt and updates silently instead.) Windows also checks every few hours in the background. The update only shows up once the release workflow has finished, which takes a few minutes. Installing the `.msix` from a Release by hand works too, but doesn't update itself.

## Using it

| | |
|---|---|
| Pen or mouse | Writes |
| Touch | Scrolls (the hand button switches fingers to writing) |
| Ask / Ctrl+Enter | The model answers what you wrote since its last answer. Nothing is sent until you ask. While an answer is coming, the button reads Stop. |
| Draw a five-point star | Asks, like the Ask button, without leaving the pen. Draw it in one stroke, apart from your writing (not on or touching it, and not on one of the model's replies). The star is taken off the page; Ctrl+Z puts it back. |
| Tap a part of a layout (web) | Selects it, if the model made it editable: drag it into a column or box that accepts drops, knob to turn, cross to delete. Nothing is sent until Ask. |
| Pen barrel button held (web), or mouse right button | Lasso: circle editable parts of a layout to select them |
| Eraser button or the pen's eraser end | Erases whole strokes |
| Ctrl+Z | Undoes the last stroke or erase |
| Conversations button | Opens the list of conversations: start a new one, switch, rename, or archive. Archived conversations are kept under **Archived** at the foot of the list, where they can still be opened, brought back, or deleted for good (tap twice). Ctrl+N starts a new one. |

Each conversation is its own page. They save themselves to the app's local folder, and the app reopens in the one you were last in. Conversations are fully separate: the model only sees the open one. Titles come from the first thing the model heard, and you can rename them. Archiving the open conversation opens the newest one left in the list (or a new one); an archived one stays archived when you open it. A conversation you never write in disappears when you move away from it, and switching while the model is answering stops that answer. The page from before conversations existed becomes the first one.

## How it gets answers

Answers come from OpenAI's models through your ChatGPT subscription, the way the Codex CLI gets them: Longhand sends the Responses API requests the CLI sends to ChatGPT's Codex backend (`chatgpt.com/backend-api/codex/responses`), with the CLI's sign-in (`Longhand.Core/CodexService.cs`, `CodexSignIn.cs`). **This isn't a public API.** OpenAI provides it for the Codex CLI, so it may change or stop accepting other apps without notice, and using it from another app is at your own risk under OpenAI's terms. Longhand says it is Longhand (`originator: longhand`), not the Codex CLI.

- Sign-in: paste `~/.codex/auth.json` (after `codex login` with ChatGPT) in the gear dialog. Longhand keeps the access token, the refresh token and the account id, and renews the access token itself when it is about to run out (or is refused). Refresh tokens are single-use: once Longhand renews, the Codex CLI's copy stops working and it asks you to sign in again; and once the CLI renews, Longhand says to paste a fresh `auth.json`.
- Nothing is stored on OpenAI's side (`store: false`): each request carries the instructions, the earlier page and, during tool use, the model's encrypted reasoning and the tool results. A per-conversation `prompt_cache_key` lets the backend reuse what it has seen.
- Only the ink written since the last answer is sent, as a PNG of black ink on white (`Services/InkSnapshot.cs`). Answers are written at the end of the page, not under the ink that prompted them. That lets you annotate an old answer: when new ink overlaps earlier replies, the picture also shows those replies in blue and the writing they answered in grey, with your new ink in black on top, and the model is told the black ink is an annotation.
- Earlier turns go along as text: the model's one-line transcription of what you wrote, plus its reply (the latest 12), so old images aren't sent again.
- The asking star is recognised on the device, with no model and no network (`StarGesture.cs`): the "$1" unistroke recogniser against built-in five-point stars from every tip, both ways round, at any tilt and proportions, plus two checks a star must pass (it closes, and it turns sharply three to five times). Tuned on synthetic strokes, it takes about 96% of deliberately messy stars and none of the look-alikes tried (circles, polygons, four- and seven-point stars, letters, zigzags, scribbles). A star only asks when it stands apart from the writing and replies and something written is waiting; otherwise it is ink. If one of your symbols is a five-point star, draw it touching the words it goes with; drawn apart, it is taken as Ask.
- Model: GPT-6.1 Sol by default, or GPT-6.1 Terra (from the Codex CLI's model catalog), asked for low reasoning effort to keep the wait short. The model is a per-conversation setting, kept in the conversation list: the dialog changes the open conversation's, and new conversations start with the one chosen last. Conversations from before this keep the default they are first opened with. Replies are streamed onto the page as they are written.
- The model can search the web (OpenAI's `web_search` tool, run on their side). While a tool runs, the answer line shows what it is doing in blue ink.
- Symbols: the gear dialog has a Symbols section for your own shortcuts, such as an envelope that means "add what I wrote to my Todoist inbox". A symbol is a name and what it means, plus an optional example drawing that you draw once on a small pad (it's saved as a small picture). There are no built-in symbols. On every Ask, the list goes to the model along with your handwriting; when the writing contains one of them, the model does what it means (using its tools, such as a connected Todoist), and the one-line transcription in the history notes it in brackets, like `[envelope symbol]`. The model is told to act only when it is reasonably sure it saw the symbol, and otherwise to say what it thinks it saw and ask. Up to 20 symbols. Symbols are saved as you edit them, in the app's local folder, and apply to every conversation.
- Connected apps (MCP servers): Longhand is the MCP client itself, since ChatGPT's backend doesn't call MCP servers (`Longhand.Core/McpClient.cs`). Before each answer it opens a session with each app over MCP's Streamable HTTP transport (answers as JSON or as an event stream; protocol `2025-06-18`), lists its tools and offers them to the model as functions named after the app (`todoist__add_task`); when the model calls one, Longhand calls the app and hands back what it returned (text; images and other content are only mentioned). Sessions and tool lists are kept for ten minutes. An app that can't be reached, or whose sign-in can't be renewed, is left out of that answer and named on the page. Servers on the older HTTP+SSE transport aren't supported. The tokens stay with Longhand: only the tools' names, descriptions and results go to OpenAI.
- MCP registry: the connected-apps dialog can search the official MCP registry (registry.modelcontextprotocol.io) and add any server found there that is hosted online. Servers that you would have to run on your own PC, that sit on a private network, or that need a header other than `Authorization: Bearer` are left out (and counted), because Longhand calls them over HTTP and can't run programs. When a server is added the app asks it how it lets you in: nothing (usable straight away), a browser sign-in (the OAuth flow above), or an access token that you get from the service and paste once ("Add token"; stored in Credential Manager). A server whose address has blanks, such as an account or region, asks for them first. Anyone can publish to the registry, so only add servers you trust.
- Nextcloud calendar: the link button's dialog has a Nextcloud section. Type your server's address and Connect: your browser opens Nextcloud's own sign-in page (Login Flow v2), you approve it, and Nextcloud hands the app an app password, so nothing is typed or pasted. The app password is stored in Windows Credential Manager. While connected, the model can read your calendar and, when you ask, add, change or delete events. Reading (`calendar_events`): the app asks your Nextcloud over CalDAV (repeating events are expanded by the server) and hands the model the agenda for the range it asked for, in your time zone, with each event's id. Writing: `calendar_add_event` adds an event to your default calendar (or one you name), `calendar_change_event` changes an event's title, time, location or notes, and `calendar_delete_event` deletes one. The model is told to change things only when you asked, to look an event up before changing or deleting it, and to say what it did. A change or deletion only goes through if the event is still as it was read (ETag), calendars shared with you read-only stay untouched, and repeating events are never changed or deleted (the model says to do that in your calendar app). Only the events the model asks for are sent to OpenAI. Disconnect revokes the app password on the server.
- Layouts and drawings: under its words the model can add up to three blocks. **There is no HTML**: structure (a board, a list, a table, columns, a tree, a set-out sum) is a **layout**, and a picture (a diagram, sketch, chart, map) is inline **SVG**.
  - A layout is written in a small language (`Longhand.Core/Layout.cs`): `<layout id="…" title="…">` holding `row` (children side by side, sharing the width; `fit` sizes a child to its content), `col` (one under another), `box` (a bordered card, words can go straight in it), `text` and `rule`, with `title` for a heading. There are no sizes, colours or coordinates to write: the host turns it into escaped HTML and CSS flex for the sandboxed frame and the browser lays it out and wraps the words. It is parsed by the app's own reader, which keeps only these elements and attributes (scripts, styles and pictures go with their content; at most 300 parts and 10 levels deep), and saved in its canonical text form. `color="red"` on any part changes its words and lines (borders, rules), and everything inside it, to that colour, and `bg="yellow"` gives it a soft tinted background. The names are red, orange, yellow, green, teal, blue, purple, pink, brown and gray; each has a light and a dark value, so they stay readable when the page follows the dark theme (the picture sent to the model always uses the light ones). `#rgb` and `#rrggbb` also work but don't adapt to the theme; anything else is dropped, so a colour can't carry CSS or a URL. `edit` on a part and `drop` on a row, column or box make it interactive (below). Example: `<layout id="board"><row><col id="todo" drop title="To do"><box id="c1" edit>Call Anna</box></col><col id="doing" drop title="Doing"/></row></layout>`.
  - Pictures are cleaned with an allowlist (HtmlSanitizer) before they are shown or saved: no scripts, event handlers, links, images or HTML, and nothing that could be fetched (`Longhand.Core/Svg.cs`). They are static: nothing in an SVG can be edited. Colours work there too, as ordinary `fill` and `stroke` values (the layout palette names don't); `currentColor` is the ink colour and follows the theme. Both kinds are rendered from a document that forbids running or loading anything, as tall as their content at the page's text width and scaled down past 1200px. Writing over one puts it in the picture sent to the model, as for words.
  - In later turns the model reads a layout as its current text (it is short), and a picture as a stand-in (`[drawing: id "house", A house]`). On the web a block is a sandboxed frame; on Windows one hidden WebView2 renders each block to a picture. Drawings saved in the old `<figure>` wrapper are unwrapped to the SVG inside; tables and other HTML in older saved pages are no longer shown.
- Editable layouts: the user can **select, move, turn and delete** parts marked `edit`, and move them into containers marked `drop`; nothing else. Every drag is structural: a part goes into a container at a place among its parts (a drop between two parts sets the place), and the page snaps it in; there are no free positions. Rotate is a `rot` attribute on the part. Edits are local: they change the page at once and are made in the saved layout, but nothing is sent to the model until the user taps **Ask** (or draws the star), and an edit alone is enough to ask. Ask then sends one line per changed part, in the same language as the layout: `c1 "Call Anna": moved from #todo (position 1) to #doing (position 2 of 3)`, `turned 15° clockwise`, or `deleted (it was in #todo (position 2))`; the layout as it is now is already in the conversation the model reads. What an edit *means* is left to the model: it acts on it with its tools (a card moved to another column can mean a changed status) only when the meaning is clear, and otherwise says what it thinks happened and asks. A layout whose root has an `id` is replaced in place when the model writes one with the same id (the board stays where it is; Ctrl+Z brings the old one back); a new id adds a new block. Ctrl+Z also takes edits back, and edits not yet told survive a restart (they are saved with the page). The browser only works out *where* a drag lands (which container is under the pointer, before which part); the server changes the layout (`Layout.ApplyEdits`), sends it back, and reports the changes (`Layout.DescribeEdits`) by comparing where each part was before the user's first change with where it is now, so a part moved away and back is not reported. Only parts with `edit` can be changed, and only into containers with `drop` (not into themselves); a change that isn't allowed is refused whole and the page shows the layout as it is.
  - Selecting: tap a part with the pen (or click it with the mouse); a dashed frame appears with a knob above it to turn the part and a cross at its corner to delete it, and dragging inside the frame moves it (a line shows where it would land; dropping it where nothing accepts it puts it back). Hold the pen's barrel button (or the mouse's right button) and circle parts to select several; it selects the parts the loop mostly encloses, in one layout. Esc or writing elsewhere puts the selection away; Delete deletes it. A tap that follows other ink within a second and close to it (the dot of an i, a full stop) stays ink and doesn't select. A finger tap selects too; fingers still scroll.
  - **On Windows editing isn't built yet** (see below): layouts there are pictures, so the model is told the device can't edit, and it doesn't use `edit` or `drop`.
- Connected apps: the link button opens a list of MCP servers (a preset for Todoist, or any https address). Sign in opens your browser; the sign-in is a standard OAuth flow that the app runs itself (the server is found automatically, the app registers itself with it, and tokens are renewed in the background). The browser comes back to the app through `callback.html` on the update site and the `longhand://` address, so the first sign-in only works once the update site is deployed. Apps must be at an https address on the internet (a rule kept from when Anthropic's servers called them). Tokens are stored in Windows Credential Manager.

## Web version

The same notebook runs in a browser, from a server on Linux (or anywhere .NET 10 runs). The server runs the shared C# code
(`Longhand.Core`: asking the model, replies, drawings, conversations, symbols, saving); the browser shows the page on an HTML canvas,
with the handwriting font, and does the two things only a browser can: measure text and draw the picture the model reads.

```
export LONGHAND_CODEX_SIGNIN="$(cat ~/.codex/auth.json)"   # or paste auth.json with the gear button in the page
dotnet run --project Longhand.Web           # then open http://127.0.0.1:5080
# on Nix: nix shell nixpkgs#dotnet-sdk_10 -c dotnet run --project Longhand.Web
```

- Options: `--urls http://127.0.0.1:5080` (or `LONGHAND_URLS`) and `--data <folder>` (or `LONGHAND_DATA`; the default is `~/.local/share/longhand`). Conversations (each with its model), symbols, the model new conversations start with, and a ChatGPT sign-in pasted into the page are kept there (`chatgpt-signin.json`, readable only by you; a pasted one wins over `LONGHAND_CODEX_SIGNIN`, and renewals are saved to it).
- Development: `nix run .#dev` (or `dotnet watch --project Longhand.Web --no-hot-reload run -- --www $PWD/Longhand.Web/wwwroot`, with an absolute path because `dotnet watch` runs the server from the project folder) serves the page from the folder instead of from inside the program, so editing `wwwroot` needs no rebuild; open tabs reload themselves when a file changes, and again when the server comes back after a restart (C# edits restart it under `dotnet watch`). Without `--www` (or `LONGHAND_WWW`) none of this is on.
- Use one tab at a time: each open tab runs its own copy of the page and saves it, so two tabs on the same conversation overwrite each other.
- **There is no sign-in.** It listens on loopback by default and refuses requests addressed to another name (DNS rebinding) and writes from another site. To use it from another device, tunnel to it (`ssh -L 5080:127.0.0.1:5080 host`) rather than exposing it.
- Typing: the keyboard button opens a box above the toolbar. Enter sends (Shift+Enter starts a new line); the note goes on the page in your ink colour, below anything you have written, and the model answers beneath it. Writing that is waiting to be answered is sent along with it. If the answer fails, the words go back into the box. Up to 4000 characters. The Windows app has the same box (keyboard button in the toolbar); both use the shared `PageSession.TypeAsync`.
- Write with a pen or mouse; fingers scroll unless you turn on the hand button. The pen's eraser end works, as does the eraser button. Replies, drawings, annotation of earlier replies, undo, conversations and symbols work as in the Windows app, and asking is the same (Ask or Ctrl+Enter; nothing is sent by itself).
- Connected apps work as in the Windows app (the link button), called by the server: MCP servers from the registry search or by address, with a browser sign-in, a pasted token or nothing, and the Nextcloud calendar. The server does the OAuth itself and keeps tokens in `secrets.json` in the data folder (readable only by you); the sign-in returns to `<this server>/oauth/callback`, so open the page at the address you sign in from (`http://127.0.0.1:5080`, or whatever your tunnel exposes). Apps must be at an https address on the internet; addresses on private networks are refused. The calendar and "now" in the prompt follow the browser's time zone. For testing only: `LONGHAND_REGISTRY_URL` and `LONGHAND_ALLOW_PRIVATE_APPS=1`.
- The code is shared like this: `PageSession` (in `Longhand.Core`) is the page: strokes waiting to be answered, notes, asking, undo, saving, conversations. It talks to its screen through `IPageView` and to storage through `IPageData`. The Windows `MainPage` is one implementation (XAML and Windows Ink), `WebConnection` the other (JSON over a WebSocket to `wwwroot/app.js`). A conversation saved by one isn't read by the other: the web version keeps ink as JSON points rather than ISF.
- Checks: `dotnet run --project tools/WebCheck/WebCheck.csproj` plays a browser over a real WebSocket against a fake API; `tools/BrowserCheck/run.sh` drives headless Chrome over the DevTools protocol (needs node 22), including tapping, dragging into a column, turning, deleting and lassoing parts of a layout, and asking with only edits.

## What was checked, and what wasn't

This was written on Linux, where UWP can't be built: the Windows build on CI is what compiles the XAML page, and what it does on a real device is only known when someone runs it. Checked here:

- `tools/CoreCheck` checks the Codex service against a fake of the backend: the pasted sign-in, the request (headers, instructions, earlier page, picture, tools, `store: false`), streaming, the tool loop with encrypted reasoning, renewing the sign-in, and errors. The real backend can't be reached from where this was written, so the first real request is the test of the shapes taken from the Codex CLI's source.
- `tools/WinRtCheck` compiles the ink snapshot, credential storage and page saving code against the Windows SDK API definitions.
- `tools/CoreCheck` also plays the notebook page (`PageSession`) against a fake screen and a fake API: asking, annotating, undo, conversations, saving, switching mid-answer.
- `tools/WebCheck` starts the web server and plays a browser over a real WebSocket; `tools/BrowserCheck` drives headless Chrome through the real page. Both run on CI.

**Editable layouts on Windows were not built or tried.** The shared code (`Layout`, `PageSession.EditDrawing`, the change list sent to the model) works on both, and the drop logic needs only the layout's tree and the box of each part. What is missing is the Windows screen: pointer routing for the tap and the barrel-button lasso (`InkPresenter.UnprocessedInput` with `RightDragAction = LeaveUnprocessed`), a selection layer over the rendered picture with a drag preview, and the boxes of each part from `BlockRenderer` (the hidden WebView2 runs no scripts, so `DOM.getBoxModel` over the DevTools protocol is the likely way; whether that works there is unchecked). After a drop the layout is rendered again, so a move there costs one more render. Until then `MainPage` answers `CanEdit => false`, so the model is told not to offer it. The Windows changes made for the layout language (`Blocks.Fit`, `Blocks.Document`, `DrawingChanged`) were also not compiled here.

Expect a round of small fixes on the first Windows build. The most likely spots:
- The `.csproj` properties for UWP on .NET 9
- `TextNudge` in `MainPage.xaml.cs`, which lines the model's text up with the ruled lines

The handwriting font is **Ink Free**, which comes with Windows 10 1803 and later. If it's missing, the app falls back to Segoe Print.
