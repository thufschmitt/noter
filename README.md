# Longhand for Windows

A native Windows prototype of Longhand: one endless ruled notebook page. Write with a pen. When you tap **Ask** (or press Ctrl+Enter), an OpenAI model, through your ChatGPT subscription, writes its answer in blue handwriting on the lines just below your ink, and anything further down moves to make room.

It reads the pen's raw pointer input (`Services/PenInput.cs`): pressure, the eraser end and the barrel button, with every sample the digitizer took. The stroke being written is drawn a little ahead of the last sample by a predictor of its own (`Longhand.Core/StrokePredictor.cs`), which does what Windows Ink's low-latency path did inside `InkCanvas`, so nothing depends on UWP's ink presenter (see **Pen input** below). The finished strokes are still kept and drawn by an `InkCanvas` whose input is off.

## Requirements

- Windows 10 version 1809 or later, or Windows 11
- Visual Studio 2022 17.14 or later, or Visual Studio 2026, with the **Universal Windows Platform tools** workload. This is UWP on modern .NET 10.
- A ChatGPT subscription, and the Codex CLI signed in with it (Longhand uses its sign-in, see below)

## Build and run

With Nix, `nix develop` gives you everything for the Linux side (.NET 10, Node, Chromium), `nix run .#web` starts the web version and `nix run .#check` runs every check that works off Windows.

1. Open `Longhand/Longhand.csproj` in Visual Studio.
2. Pick your platform (x64 or ARM64) and press F5. Visual Studio restores the NuGet packages, deploys the app and starts it.
3. Sign in to the Codex CLI with ChatGPT (`codex login`), click the gear button and paste the contents of `~/.codex/auth.json`. It's stored in Windows Credential Manager, not in any file.

If Visual Studio won't load the project file, create a new project from the **UWP Blank App** template (the .NET one), name it `Longhand`, then:
- Add the `HtmlSanitizer` NuGet package.
- Copy `MainPage.xaml`, the `MainPage*.cs` files and the `Services` folder into the new project.
- Add `<PublishAot>false</PublishAot>` to the new project's csproj.

## Installing and updating

Every push to `main` builds signed packages and publishes them as a GitHub Release. A small GitHub Pages site next to it holds the `.appinstaller` files that tell Windows which version is newest; they point at the packages on the Release.

One-time setup of the repository: Settings → Pages → Source: **GitHub Actions**.

One-time setup of each PC:

1. Trust the certificate, in an administrator terminal: `certutil -addstore TrustedPeople Longhand.cer`
2. Open the `.appinstaller` link for your PC (x64 or ARM64) and choose Install. They are `https://thufschmitt.github.io/noter/Longhand-x64.appinstaller` and `https://thufschmitt.github.io/noter/Longhand-arm64.appinstaller`.

After that, starting the app from the Start menu or a tile checks for a newer version first and asks to install it before the app opens. (A taskbar or desktop shortcut skips the prompt and updates silently instead.) Windows also checks every few hours in the background. The update only shows up once the release workflow has finished, which takes a few minutes. Installing the `.msix` from a Release by hand works too, but doesn't update itself.

## Using it

| | |
|---|---|
| Pen or mouse | Writes |
| Touch | Scrolls (the hand button switches fingers to writing) |
| Pinch with two fingers | Zooms (Ctrl with the mouse wheel too). Only in, never smaller than the page at its full width: on Windows up to four times, and the sheet scrolls sideways when zoomed in; on the web it is the browser's own pinch zoom, and the ink is redrawn sharp at the new size. Writing, erasing and editing work the same zoomed. A pinch that starts while a finger is writing drops that stroke. |
| Ask / Ctrl+Enter | The model answers what you wrote since its last answer. Nothing is sent until you ask. While an answer is coming, the button reads Stop. |
| Draw a five-point star | Asks, like the Ask button, without leaving the pen. Draw it in one stroke anywhere on the page, as long as no other ink is close to it (not on or touching your writing). The star is taken off the page; Ctrl+Z puts it back. |
| Tap a part of a layout | Selects it, if the model made it editable: drag it into a column or box that accepts drops, knob to turn, cross to delete. Nothing is sent until Ask. |
| Pen barrel button held, or mouse right button | Lasso: circle editable parts of a layout to select them |
| Eraser button or the pen's eraser end | Erases whole strokes |
| Ctrl+Z | Undoes the last stroke or erase |
| Conversations button | Opens the list of conversations: start a new one, switch, rename, or archive. Archived conversations are kept under **Archived** at the foot of the list, where they can still be opened, brought back, or deleted for good (tap twice). Ctrl+N starts a new one. |

Each conversation is its own page. They save themselves to the app's local folder, and the app reopens in the one you were last in. Conversations are fully separate: the model only sees the open one. Titles come from the first thing the model heard, and you can rename them. Archiving the open conversation opens the newest one left in the list (or a new one); an archived one stays archived when you open it. A conversation you never write in disappears when you move away from it, and switching while the model is answering stops that answer. The page from before conversations existed becomes the first one.

## How it gets answers

Answers come from OpenAI's models through your ChatGPT subscription, the way the Codex CLI gets them: Longhand sends the Responses API requests the CLI sends to ChatGPT's Codex backend (`chatgpt.com/backend-api/codex/responses`), with the CLI's sign-in (`Longhand.Core/CodexService.cs`, `CodexSignIn.cs`). **This isn't a public API.** OpenAI provides it for the Codex CLI, so it may change or stop accepting other apps without notice, and using it from another app is at your own risk under OpenAI's terms. Longhand says it is Longhand (`originator: longhand`), not the Codex CLI.

- Sign-in: paste `~/.codex/auth.json` (after `codex login` with ChatGPT) in the gear dialog. Longhand keeps the access token, the refresh token and the account id, and renews the access token itself when it is about to run out (or is refused). Refresh tokens are single-use: once Longhand renews, the Codex CLI's copy stops working and it asks you to sign in again; and once the CLI renews, Longhand says to paste a fresh `auth.json`.
- Nothing is stored on OpenAI's side (`store: false`): each request carries the instructions, the earlier page and, during tool use, the model's encrypted reasoning and the tool results. A per-conversation `prompt_cache_key` lets the backend reuse what it has seen.
- Only the ink written since the last answer is sent, as a PNG of black ink on white (`Services/InkSnapshot.cs`). Answers are written at the end of the page, not under the ink that prompted them. That lets you annotate an old answer: when new ink overlaps earlier replies, the picture also shows those replies in blue and the writing they answered in grey, with your new ink in black on top, and the model is told the black ink is an annotation.
- Earlier turns go along as text: the model's one-line transcription of what you wrote, plus its reply (the latest 12), so old images aren't sent again.
- The asking star is recognised on the device, with no model and no network (`StarGesture.cs`): the "$1" unistroke recogniser against built-in five-point stars from every tip, both ways round, at any tilt and proportions, plus two checks a star must pass (it closes, and it turns sharply three to five times). Tuned on synthetic strokes, it takes about 96% of deliberately messy stars and none of the look-alikes tried (circles, polygons, four- and seven-point stars, letters, zigzags, scribbles). A star only asks when it stands apart from the writing and replies and something written is waiting; otherwise it is ink. If one of your symbols is a five-point star, draw it touching the words it goes with; drawn apart, it is taken as Ask.
- Model: GPT-6.1 Sol by default, or GPT-6.1 Terra (from the Codex CLI's model catalog), asked for low reasoning effort to keep the wait short. The model is a per-conversation setting, kept in the conversation list: the dialog changes the open conversation's, and new conversations start with the one chosen last. Conversations from before this keep the default they are first opened with. Replies are streamed onto the page as they are written.
- The model can search the web (OpenAI's `web_search` tool, run on their side). While a tool runs, the answer line shows what it is doing in blue ink.
- Symbols: the gear dialog has a Symbols section for your own shortcuts, such as an envelope that means "add what I wrote to my Todoist inbox". A symbol is a name and what it means, plus an optional example drawing that you draw once on a small pad (it's saved as a small picture). There are no built-in symbols. On every Ask, the list goes to the model along with your handwriting; when the writing contains one of them, the model does what it means (using its tools, such as a connected Todoist), and the one-line transcription in the history notes it in brackets, like `[envelope symbol]`. The model is told to act only when it is reasonably sure it saw the symbol, and otherwise to say what it thinks it saw and ask. Up to 20 symbols. Symbols are saved as you edit them, in the app's local folder, and apply to every conversation.
- Connected apps (MCP servers): Longhand is the MCP client itself, since ChatGPT's backend doesn't call MCP servers (`Longhand.Core/McpClient.cs`). Before each answer it opens a session with each app over MCP's Streamable HTTP transport (answers as JSON or as an event stream; protocol `2025-06-18`), lists its tools and offers them to the model as functions named after the app (`todoist__add_task`); when the model calls one, Longhand calls the app and hands back what it returned (text; images and other content are only mentioned). Sessions and tool lists are kept for ten minutes. An app that can't be reached, or whose sign-in can't be renewed, is left out of that answer and named on the page. Servers on the older HTTP+SSE transport aren't supported. The tokens stay with Longhand: only the tools' names, descriptions and results go to OpenAI.
- MCP registry: the connected-apps dialog can search the official MCP registry (registry.modelcontextprotocol.io) and add any server found there that is hosted online. Servers that you would have to run on your own PC, that sit on a private network, or that need a header other than `Authorization: Bearer` are left out (and counted), because Longhand calls them over HTTP and can't run programs. When a server is added the app asks it how it lets you in: nothing (usable straight away), a browser sign-in (the OAuth flow above), or an access token that you get from the service and paste once ("Add token"; stored in Credential Manager). A server whose address has blanks, such as an account or region, asks for them first. Anyone can publish to the registry, so only add servers you trust.
- Nextcloud calendar: the link button's dialog has a Nextcloud section. Type your server's address and Connect: your browser opens Nextcloud's own sign-in page (Login Flow v2), you approve it, and Nextcloud hands the app an app password, so nothing is typed or pasted. The app password is stored in Windows Credential Manager. While connected, the model can read your calendar and, when you ask, add, change or delete events. Reading (`calendar_events`): the app asks your Nextcloud over CalDAV (repeating events are expanded by the server) and hands the model the agenda for the range it asked for, in your time zone, with each event's id. Writing: `calendar_add_event` adds an event to your default calendar (or one you name), `calendar_change_event` changes an event's title, time, location or notes, and `calendar_delete_event` deletes one. The model is told to change things only when you asked, to look an event up before changing or deleting it, and to say what it did. A change or deletion only goes through if the event is still as it was read (ETag), calendars shared with you read-only stay untouched, and a repeating event is changed or deleted one occurrence at a time: its id in the agenda is `file#start` (for example `personal/a.ics#20261118T080000Z`), so moving or editing one instance changes only that occurrence, as an exception in the event's file (`RECURRENCE-ID`), and deleting one leaves its date out of the rule (`EXDATE`). `scope: "all"` (only when you clearly mean every occurrence) changes the event itself, its title, place or notes but never its times, or deletes the whole series. **Choosing calendars**: under the connection the dialog lists your calendars as tick boxes (calendars shared read-only are marked); the model only uses the ticked ones, and a tick is saved as soon as it is made. Until you choose, it uses all of them. An unticked calendar is not read, not added to, and its events are neither changed nor deleted, even if the model has an id from before; ticking none leaves the model without the calendar. Only the events the model asks for are sent to OpenAI. Disconnect revokes the app password on the server.
- Layouts and drawings: under its words the model can add up to three blocks. **There is no HTML**: structure (a board, a list, a table, columns, a tree, a set-out sum) is a **layout**, and a picture (a diagram, sketch, chart, map) is inline **SVG**.
  - A layout is written in a small language (`Longhand.Core/Layout.cs`): `<layout id="…" title="…">` holding `row` (children side by side, sharing the width; `fit` sizes a child to its content), `col` (one under another), `box` (a bordered card, words can go straight in it), `text` and `rule`, with `title` for a heading. There are no sizes, colours or coordinates to write: the host turns it into escaped HTML and CSS flex for the sandboxed frame and the browser lays it out and wraps the words. It is parsed by the app's own reader, which keeps only these elements and attributes (scripts, styles and pictures go with their content; at most 300 parts and 10 levels deep), and saved in its canonical text form. `color="red"` on any part changes its words and lines (borders, rules), and everything inside it, to that colour, and `bg="yellow"` gives it a soft tinted background. The names are red, orange, yellow, green, teal, blue, purple, pink, brown and gray; each has a light and a dark value, so they stay readable when the page follows the dark theme (the picture sent to the model always uses the light ones). `#rgb` and `#rrggbb` also work but don't adapt to the theme; anything else is dropped, so a colour can't carry CSS or a URL. A **timeline** is a `col` with the attribute `timeline` (a day's schedule, an agenda): its children are placed by time instead of stacked. A child's `start="09:00"` and `end="09:30"` (24-hour times; with no `end` an item lasts an hour) put it on a grid of hours, as tall as it is long (64px to the hour); items that overlap split the width side by side (the host works the lanes out from the times, so it needs no text measuring); an item with no `start` is listed above the grid. `timeline="08:00-18:00"` sets the hours shown (a bare `timeline` fits the items, and an item outside the range widens it to whole hours; nothing says 08:00–18:00). Timeline columns side by side share the widest range, so the days of a week (a `row` of them) line up, and only the first writes the hours. Times mean something only in a timeline column (they're dropped elsewhere), and items there aren't turned. Example: `<col id="thu" timeline="08:00-18:00" drop title="Thu 12"><box id="e1" edit start="09:00" end="09:30">Standup</box></col>`. `edit` on a part and `drop` on a row, column or box make it interactive (below). Example: `<layout id="board"><row><col id="todo" drop title="To do"><box id="c1" edit>Call Anna</box></col><col id="doing" drop title="Doing"/></row></layout>`.
  - Pictures are cleaned with an allowlist (HtmlSanitizer) before they are shown or saved: no scripts, event handlers, links, images or HTML, and nothing that could be fetched (`Longhand.Core/Svg.cs`). They are static: nothing in an SVG can be edited. Colours work there too, as ordinary `fill` and `stroke` values (the layout palette names don't); `currentColor` is the ink colour and follows the theme. Both kinds are as tall as their content at the page's text width (on the web a layout is scaled down past 1200px, and a picture is at most 480px tall). Writing over one puts it in the picture sent to the model, as for words.
  - In later turns the model reads a layout as its current text (it is short), and a picture as a stand-in (`[drawing: id "house", A house]`). Drawings saved in the old `<figure>` wrapper are unwrapped to the SVG inside; tables and other HTML in older saved pages are no longer shown.
- Editable layouts: the user can **select, move, turn and delete** parts marked `edit`, and move them into containers marked `drop`; nothing else. Every drag is structural: a part goes into a container at a place among its parts (a drop between two parts sets the place), and the page snaps it in; there are no free positions. In a timeline column the place is a time: dragging an `edit` item changes its start (keeping its length, in steps of 15 minutes, kept inside the day) and can drop it into another timeline column (another day), and dragging its bottom handle changes its end (at least 15 minutes after the start). A timeline column always lets its own items change time; receiving items from elsewhere takes `drop`, and an item with no time dropped in gets an hour. Rotate is a `rot` attribute on the part. Edits are local: they change the page at once and are made in the saved layout, but nothing is sent to the model until the user taps **Ask** (or draws the star), and an edit alone is enough to ask. Ask then sends one line per changed part, in the same language as the layout (in a timeline, in times: `e2 "Dentist": rescheduled from 14:00–15:30 to 10:00–11:30`, `resized from 14:00–15:30 to 14:00–16:00`, `moved from #thu 14:00–15:30 to #fri 10:00–11:30`): `c1 "Call Anna": moved from #todo (position 1) to #doing (position 2 of 3)`, `turned 15° clockwise`, or `deleted (it was in #todo (position 2))`; the layout as it is now is already in the conversation the model reads. What an edit *means* is left to the model: it acts on it with its tools (a card moved to another column can mean a changed status) only when the meaning is clear, and otherwise says what it thinks happened and asks. A layout whose root has an `id` is replaced in place when the model writes one with the same id (the board stays where it is; Ctrl+Z brings the old one back); a new id adds a new block. Ctrl+Z also takes edits back, and edits not yet told survive a restart (they are saved with the page). The browser only works out *where* a drag lands (which container is under the pointer, before which part); the server changes the layout (`Layout.ApplyEdits`), sends it back, and reports the changes (`Layout.DescribeEdits`) by comparing where each part was before the user's first change with where it is now, so a part moved away and back is not reported. Only parts with `edit` can be changed, and only into containers with `drop` (not into themselves); a change that isn't allowed is refused whole and the page shows the layout as it is.
  - Selecting: tap a part with the pen (or click it with the mouse); a dashed frame appears with a knob above it to turn the part and a cross at its corner to delete it, and dragging inside the frame moves it (a line shows where it would land, with the time written on it on a timeline; dropping it where nothing accepts it puts it back). A single item of a timeline has a handle at the bottom of its frame instead of the turn knob, to drag its end. Hold the pen's barrel button (or the mouse's right button) and circle parts to select several; it selects the parts the loop mostly encloses, in one layout. Esc or writing elsewhere puts the selection away; Delete deletes it. A tap that follows other ink within a second and close to it (the dot of an i, a full stop) stays ink and doesn't select. A finger tap selects too; fingers still scroll.
  - **Erasing your marks.** Once what you wrote on top of a block no longer makes sense (a tick for something done, a circle round a part it redrew), the model can erase it: after its words it writes `<erase over="board"/>` (the block's id), or with `x`, `y`, `w`, `h` (fractions of the block from its top left) for only a part of it (`Longhand.Core/InkErase.cs`). Only your ink that lies mostly inside the block or region goes, never anything else; it is taken off the page like the eraser does, one Undo brings all of it back, the page says how many strokes went, and the model is told to say in its words what it erased. It can only judge marks it has been shown, which are the ones you wrote over its replies since it last answered. A block's place on the page is worked out from its note (`PageSession`), so the region is as exact as the block's measured height.
  - **How each platform draws them.** On the web a block is a sandboxed frame (it runs nothing and loads nothing) that the browser lays out from escaped HTML and CSS. On Windows nothing is a picture: a layout is built as native XAML controls from the same tree (`row` a `Grid`, `col` a `StackPanel`, `box` a `Border`, a timeline column a `TimelinePanel`; `Services/LayoutXaml.cs`), so XAML measures the words and every part is a control that can be found and moved; a picture is its SVG read into a scene (`Longhand.Core/SvgScene.cs`: groups, paths, text, with every style worked out) and built as XAML shapes and text (`Services/SvgXaml.cs`). Windows' own SVG renderer (`SvgImageSource`) isn't used because Direct2D skips `<text>`. Markers, masks, clip paths and patterns aren't drawn on Windows, a gradient is drawn as its first colour, and a Windows layout is not scaled down when it is very tall. WebView2 and WinUI 2 are no longer part of the app.
  - **Editing works the same on Windows**, over the controls: a tap with the pen (a stroke that is only a tap, on a part, is taken off the page so it leaves no dot, unless it follows other ink closely), a click or a finger tap selects; the barrel button or the right mouse button draws a lasso (`PenInput` hands its points over instead of writing). The frame, turn knob, cross and end handle are controls above the ink layer, and while the pointer is over them writing is switched off, so the pen grabs instead of writing. While a part is moved the real one stays where it is, dimmed, and a copy follows the pointer, with the same drop line and time label as on the web. Delete and Esc work. The arithmetic (which container, which place, which time, what a lasso takes) is `LayoutHit` in the Core, with checks; the changes go through the same `PageSession.EditDrawing`.
- Your own OAuth client, for MCP servers that don't let apps register themselves: the add-by-address form (web and Windows) has an optional **sign-in client**: a client ID, a client secret if it has one, and the scopes to ask for (leave empty to use what the server asks for). With it, Longhand doesn't register itself but signs in as that client, sends the secret when it trades the code and when it renews the token, and, when the service has no `offline_access` scope (Google's doesn't), asks for offline access (`access_type=offline`, `prompt=consent`) so a refresh token comes back instead of an hourly sign-in. The client ID is kept with the app, the secret as a secret (Credential Manager, or `secrets.json`), and signing out keeps both so signing in again is one tap; removing the app forgets them. The redirect address to register with the service is shown in the form: the web version's is `<this server>/oauth/callback`, Windows' is `https://thufschmitt.github.io/noter/callback.html`.
- Google Calendar, through Google's own API: the apps dialog (web and Windows) has a **Google Calendar** section. Google doesn't let apps register themselves, so it uses an OAuth client that you make once in your own Google Cloud project: enable the **Google Calendar API**, set up the OAuth consent screen (add yourself as a test user), create a **Web application** client, and register the redirect address the dialog shows (the web version's is `<this server>/oauth/callback`, e.g. `http://127.0.0.1:5080/oauth/callback`; Windows' is `https://thufschmitt.github.io/noter/callback.html`; one client can have both). Paste the client ID and secret and **Connect**; you approve it in your browser. The model then gets `google_calendar_events`, which reads the events of the calendars to use (repeating ones as the single occurrences in the range) as the same agenda the Nextcloud calendar gives, each with an `{id: calendar|event}`. **Choosing calendars**: once connected, the dialog lists your Google calendars as tick boxes (read-only ones are marked) and a tick is saved as soon as it is made. Until you choose, the model uses the calendars switched on in Google Calendar itself, plus your main one; once you have, exactly the ticked ones (so a calendar Google has switched off can be ticked, and your main one unticked). An unticked calendar is not read, not added to, and its events are neither changed nor deleted; ticking none leaves the model without the calendar. Disconnecting forgets the choice, as another Google account has other calendars. By default it asks Google for read-only access (`calendar.calendarlist.readonly`, `calendar.events.readonly`, which a consent screen set up for read-only access already lists). **Also let the model add, change and delete events** asks for `calendar.events` instead and adds `google_calendar_add_event`, `google_calendar_change_event` and `google_calendar_delete_event`, with the same rules as for Nextcloud: only when you asked, look an event up first, a change or deletion goes through only if the event is still at the version that was read (Google's etag, sent as `If-Match`), calendars shared read-only can't be changed, and a repeating event is changed or deleted one occurrence at a time, which is what Google does when an occurrence's own id is patched or deleted; `scope: "all"` (only when you clearly mean every occurrence) changes the event itself, but not its times, or deletes the series. Changing that box (or the client) forgets the sign-in, so you connect again. The client secret and the tokens are kept as secrets (Credential Manager, or `secrets.json`); the token is renewed when it runs low (offline access is asked for, so it keeps working), **Disconnect** revokes it with Google and keeps the client, and **Forget client** removes everything. Google's own *Calendar MCP server* (`calendarmcp.googleapis.com`) is not used: it needs the Workspace Developer Preview Program. **Not tried against Google itself**: the API paths, the sign-in and the version tags were written from Google's documentation and checked against a fake that behaves like it; the first real connection is the test. While the consent screen is in "testing", Google may expire refresh tokens after 7 days (then connect again). Event text written by other people reaches the model, so the usual prompt-injection caution applies, most of all with changes allowed.
- Connected apps: the link button opens a list of MCP servers (a preset for Todoist, or any https address). Sign in opens your browser; the sign-in is a standard OAuth flow that the app runs itself (the server is found automatically, the app registers itself with it, and tokens are renewed in the background). The browser comes back to the app through `callback.html` on the update site and the `longhand://` address, so the first sign-in only works once the update site is deployed. Apps must be at an https address on the internet (a rule kept from when Anthropic's servers called them). Tokens are stored in Windows Credential Manager.

## Pen input

The Windows app reads the pen as plain pointer events (`Services/PenInput.cs`), not through UWP's ink presenter, so that it can move off UWP (and onto Linux) without losing the low latency that `InkCanvas` gave. What `InkCanvas` did for us is done here:

- **Prediction** (`Longhand.Core/StrokePredictor.cs`, no platform code). The stroke being written is drawn up to 25 ms ahead of the last sample, about the time from a sample to the frame that shows it, so the line seems to stick to the nib. Each axis is followed by a Kalman filter (position, velocity, acceleration, with a random jerk as its noise) fed every sample at its own timestamp, so batched and unevenly spaced samples are fine. The guess is the filter carried forward, with the acceleration's share tapering further out; it is shortened when there are few samples yet, when the pen is barely moving (speed measured over 30 ms of samples, so the digitizer's noise doesn't count), and when recent guesses missed where the pen went (a sharp turn, a stop), and comes back once they don't. It never turns back on itself and never runs further than 1.5 times the pen's speed allows. Guesses are only drawn, never stored: each new sample replaces the last guess, and the finished stroke is built from the real samples alone. On synthetic handwriting sampled at 240 Hz with noise, the end of the ink is 2.7 px from the nib where it would be 6.9 px without prediction; on fast lines and circles about 90% of the gap is closed; a pen stopping dead at 600 px/s sees the guess run at most 3 px past the stop, gone within 50 ms (`tools/CoreCheck/PredictorChecks.cs`). The horizon is `PenInput.PredictionHorizon`: too long and the guess wobbles at turns, too short and the ink trails.
- **Wet ink**: every sample the system batched since the last event (`GetIntermediatePoints`), drawn as it comes as line segments whose width follows the pressure, plus the guess; when the pen lifts, the stroke is built with `InkStrokeBuilder` from those samples (pressure, tilt, timestamps) and the wet ink is taken away two frames later, once the ink canvas has drawn the stroke.
- **Erasing** whole strokes (the eraser button, or the pen's eraser end): a stroke goes once the eraser's path comes within 5 px of its line (`Longhand.Core/EraserHit.cs`). One pass of the eraser is one undo.
- **The lasso**: the barrel button or the right mouse button hands its points to the page instead of writing.
- **Palm rejection**, when finger writing is on: a finger doesn't write while a pen is touching or hovering, nor for a second after.

**In the browser** the same predictor runs as a line-for-line JavaScript port (`Longhand.Web/wwwroot/predictor.js`), fed every coalesced pointer event with its own timestamp, and draws its guess on a canvas of its own over the ink, cleared and drawn again with every move. It allocates nothing per sample. `tools/CoreCheck` runs the port with node on the same samples as the C# (handwriting, lines, stops, corners, pauses, repeated and out-of-order samples) and checks that the guesses agree after every one, so a change to one without the other fails; `tools/BrowserCheck` checks that a guess is drawn while writing, gone when the pen lifts, and never kept in the stroke. Both ink canvases are also `desynchronized`, so where the browser supports it (Chrome, Edge) what is drawn shows without waiting for the rest of the page to be painted. The horizon is `PREDICTION_HORIZON` in `app.js`, 25 ms like Windows; a browser's own latency is often longer, so it may want more.

**The pen demo** (`Longhand.PenDemo`) is a plain Windows program to try the predictor on a real device without installing anything: a window to write on that reads the pen with Win32's pointer messages (`WM_POINTER*`, with the history of samples batched into each, at the digitizer's sub-pixel precision and timestamps), the same `StrokePredictor`, a box to turn prediction off and on (P) to compare, the guess shown in red (R), and the horizon on a slider; the status line shows the samples per second, how many come in each message, and how sure the guess is. Once the `pen-demo` CI job is in the workflow, each GitHub Release has `LonghandPenDemo-x64.exe` and `LonghandPenDemo-arm64.exe`, and every build keeps them as the `PenDemo` artifact. They're not signed, so Windows' SmartScreen asks first (More info → Run anyway). To build one: `dotnet publish Longhand.PenDemo -c Release -r win-x64 --self-contained -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true -p:EnableCompressionInSingleFile=true` (works on Linux too). It draws with GDI+ through WinForms, which is not the fastest way to the screen, so it shows what prediction adds, not the lowest latency possible.

What still depends on Windows: the finished strokes are kept in an `InkStrokeContainer` (saved as ISF, read for the picture sent to the model and for handwriting recognition) and drawn by an `InkCanvas` with its input off. The symbol pad in the gear dialog works the same way. **Not yet tried on a device**: how the wet ink lines up with the dry stroke that replaces it (Windows smooths finished strokes, `FitToCurve`, and its pressure curve may differ from the one guessed here, `PenInput.Width`), and whether 25 ms is the right horizon on real hardware.

## When something goes wrong

Both Windows apps keep a crash log (`Services/CrashLog.cs`): every error nothing else caught is written to `crash.log` in the app's local folder (`%LOCALAPPDATA%\Packages\Longhand.Prototype_…\LocalState`), with the time, the app and its version, the Windows version, where it happened and the whole exception with its stack trace. An error that reaches the UI thread from an async method arrives without its stack, so the app also remembers the last few exceptions thrown, with where each was thrown, and adds them to such an entry (the same kind first). The page's own handlers (buttons, keys, the pen's actions) catch what their work throws (`MainPage.Guard`): it is written down with the method and line that started it, a note says so, and the app carries on. An error that still gets to Windows' last-chance handler is written down as possibly fatal, since an async one can end the app whatever that handler asks; when the app did close (because of that, or of anything else written down), it says so the next time it starts, with **Copy details**. The gear dialog's **Crash report** section copies the latest entries any time, formatted to paste into an issue or a chat, and clears them. The entries hold errors and code locations, not your pages or calendar, but read them before sharing.

## Longhand Calendar

A second app in the same package, for the calendar alone: it appears in the Start menu as **Longhand Calendar** (the package's second `<Application>`, `Id="Calendar"`; the same program, which knows it is the calendar from `CoreApplication.Id`). On the web it is the same server at **`/calendar`** (e.g. `http://127.0.0.1:5080/calendar`). It looks like the notebook, but instead of conversations the page is one day of your calendar, on the same timeline the model draws, with the day's events from every connected calendar (Google and Nextcloud, only the ticked calendars; each calendar gets its own colour when there are several).

- **Changing the day**: the bar at the top (previous, next, **Today**), or Alt+Left / Alt+Right. Another day starts afresh (the ink, the answer and undo go). The day is read again when the window or tab comes back to the front.
- **Moving and resizing events goes straight to the calendar**, with no model involved: drag an event to another time, drag its bottom handle to change its end, or delete it with the cross. Each change is made at once through the same calendar functions the model uses, so the same rules hold: only calendars you ticked, only if the event is still as it was read (ETag), and a repeating event changes one occurrence. Ctrl+Z moves an event back (a deletion can't be undone). Afterwards the day is read again from the calendar, which also puts back anything the calendar refused (the reason is shown). All-day events, events of calendars that can't be changed (read-only ones, or Google connected read-only) and events that run past midnight can't be moved there.
- **Drawing new events, with no model**: nothing in the calendar app goes to a model, and it needs no ChatGPT sign-in. Draw on the day, then tap **Add** (or draw the star): the app reads the ink itself (`Longhand.Core/InkEvents.cs`, plain geometry against the hour grid). A closed shape (a box, an oval) over the hours is an event from its top to its bottom, and the writing inside it is its title; a line or bracket down the hours does the same, with the writing to its right; writing on its own is an event of an hour from where its line starts. Times snap to 15 minutes. On Windows the title is read by Windows' own handwriting recognition, on the PC, in two languages: by default French, then English (the gear dialog's **Handwriting** section chooses a main and a second language among the recognizers installed; each needs its language's handwriting feature in Windows: Settings → Time & language → Language). Windows' recognizers don't say how sure they are, so each language's reading is checked against Windows' own spell-checking dictionary of that language (`Longhand.Core/HandwritingChoice.cs`, `Services/SpellCheck.cs`): the reading with the most real words wins, the main language on a tie, and a word the dictionary doesn't know is swapped for the recognizer's next guess that it does. When both read the same, or only one reading is all real words, it is used as it is; otherwise a box shows the best reading to confirm or correct, with the others one tap away, each marked with the language that read it (and when nothing can be read, it asks you to type the title). If the dictionaries can't be used, the main language's reading comes first and the box always asks. A browser can't read handwriting, so on the web a box asks for each title. Skip leaves an event out. The events go to the default calendar (below), the ink they were drawn with comes off the page, and Ctrl+Z deletes them again and puts the ink back. Ink that marks no event stays where it is. **Writing over an event already there renames it**: the writing (read the same way, or typed, starting from its current title) becomes its new title, unless it is inside a box you drew, which makes a new event; for a repeating event, only that occurrence is renamed, and an event of a calendar that can't be changed keeps its title. The writing comes off once it is done, and the same Ctrl+Z gives the old title back. A box must be drawn in one stroke, and an event can't be moved or deleted by writing on it (drag it, or use its cross).
- **Default calendar for new events**: the connected-apps dialog (web and Windows) has a **New events** section listing the calendars that can be changed and that are ticked, across both providers. The choice is used when no calendar is named, by the calendar app and by the notebook's model alike; with both providers connected the model is also told which one to add to. Leaving it on the first entry keeps each provider's own default (Google's main calendar, Nextcloud's personal one).
- On Windows, sign in to connected apps from the notebook: the browser comes back through `longhand://`, which opens Longhand, not Longhand Calendar. Once connected, both apps use the same sign-ins and settings.

## Web version

The same notebook runs in a browser, from a server on Linux (or anywhere .NET 10 runs). The server runs the shared C# code
(`Longhand.Core`: asking the model, replies, drawings, conversations, symbols, saving); the browser shows the page on an HTML canvas,
with the handwriting font, and does the two things only a browser can: measure text and draw the picture the model reads.

```
export LONGHAND_CODEX_SIGNIN="$(cat ~/.codex/auth.json)"   # or paste auth.json with the gear button in the page
dotnet run --project Longhand.Web           # then open http://127.0.0.1:5080
# on Nix: nix shell nixpkgs#dotnet-sdk_10 -c dotnet run --project Longhand.Web
```

- Options: `--urls http://127.0.0.1:5080` (or `LONGHAND_URLS`) and `--data <folder>` (or `LONGHAND_DATA`; the default is `~/.local/share/longhand`). Conversations (each with its model), symbols, the model new conversations start with, and a ChatGPT sign-in pasted into the page are kept there (`chatgpt-signin.json`, readable only by you; a pasted one wins over `LONGHAND_CODEX_SIGNIN`, and renewals are saved to it).
- Development: `nix run .#dev` (or `dotnet watch --project Longhand.Web --no-hot-reload run -- --www $PWD/Longhand.Web/wwwroot`, with an absolute path because `dotnet watch` runs the server from the project folder) serves the page from the folder instead of from inside the program, so editing `wwwroot` needs no rebuild; open tabs reload themselves when a file changes, and again when the server comes back after a restart (C# edits restart it under `dotnet watch`). Without `--www` (or `LONGHAND_WWW`) none of this is on.
- Use one tab at a time: each open tab runs its own copy of the page and saves it, so two tabs on the same conversation overwrite each other.
- **There is no sign-in.** It listens on loopback by default and refuses requests addressed to another name (DNS rebinding) and writes from another site. To use it from another device, tunnel to it (`ssh -L 5080:127.0.0.1:5080 host`) rather than exposing it.
- Typing: the keyboard button opens a box above the toolbar. Enter sends (Shift+Enter starts a new line); the note goes on the page in your ink colour, below anything you have written, and the model answers beneath it. Writing that is waiting to be answered is sent along with it. If the answer fails, the words go back into the box. Up to 4000 characters. The Windows app has the same box (keyboard button in the toolbar); both use the shared `PageSession.TypeAsync`.
- Write with a pen or mouse; fingers scroll unless you turn on the hand button. The stroke being written is drawn a little ahead of the pen, as on Windows (see **Pen input**). The pen's eraser end works, as does the eraser button. Replies, drawings, annotation of earlier replies, undo, conversations and symbols work as in the Windows app, and asking is the same (Ask or Ctrl+Enter; nothing is sent by itself).
- Connected apps work as in the Windows app (the link button), called by the server: MCP servers from the registry search or by address, with a browser sign-in, a pasted token or nothing, and the Nextcloud calendar. The server does the OAuth itself and keeps tokens in `secrets.json` in the data folder (readable only by you); the sign-in returns to `<this server>/oauth/callback`, so open the page at the address you sign in from (`http://127.0.0.1:5080`, or whatever your tunnel exposes). Apps must be at an https address on the internet; addresses on private networks are refused. The calendar and "now" in the prompt follow the browser's time zone. For testing only: `LONGHAND_REGISTRY_URL` and `LONGHAND_ALLOW_PRIVATE_APPS=1`.
- The code is shared like this: `PageSession` (in `Longhand.Core`) is the page: strokes waiting to be answered, notes, asking, undo, saving, conversations. It talks to its screen through `IPageView` and to storage through `IPageData`. The Windows `MainPage` is one implementation (XAML and Windows Ink), `WebConnection` the other (JSON over a WebSocket to `wwwroot/app.js`). A conversation saved by one isn't read by the other: the web version keeps ink as JSON points rather than ISF.
- Checks: `dotnet run --project tools/WebCheck/WebCheck.csproj` plays a browser over a real WebSocket against a fake API; `tools/BrowserCheck/run.sh` drives headless Chrome over the DevTools protocol (needs node 22), including tapping, dragging into a column, turning, deleting and lassoing parts of a layout, dragging an item to another day and time and stretching its end on a timeline, and asking with only edits.

## What was checked, and what wasn't

This was written on Linux, where UWP can't be built: the Windows build on CI is what compiles the XAML page, and what it does on a real device is only known when someone runs it. Checked here:

- `tools/CoreCheck` checks the Codex service against a fake of the backend: the pasted sign-in, the request (headers, instructions, earlier page, picture, tools, `store: false`), streaming, the tool loop with encrypted reasoning, renewing the sign-in, and errors. The real backend can't be reached from where this was written, so the first real request is the test of the shapes taken from the Codex CLI's source.
- `tools/WinRtCheck` compiles the ink snapshot, credential storage and page saving code against the Windows SDK API definitions.
- `tools/XamlCheck` type-checks all the rest of the Windows app's code (`MainPage` and the `Services`, the native layouts and the editing among them) against the UWP projections, with what the XAML compiler generates stubbed from `MainPage.xaml` (`nix run .#check`, or `dotnet build tools/XamlCheck`; it needs node). It finds compile errors without a Windows machine; it can't run anything.
- `tools/CoreCheck` checks what the native drawings are built from: SVG read into a scene (path data with its shorthands and run-on numbers, transforms, styles and inheritance, colours, text and `tspan` lines) and the pointer arithmetic of editing.
- `tools/CoreCheck` also plays the notebook page (`PageSession`) against a fake screen and a fake API: asking, annotating, undo, conversations, saving, switching mid-answer.
- `tools/WebCheck` starts the web server and plays a browser over a real WebSocket; `tools/BrowserCheck` drives headless Chrome through the real page. Both run on CI.

**The native layouts, drawings and their editing on Windows have been compiled but never run.** Nothing here can run UWP, so the first real test is a Windows device with a pen. What is most likely to need a fix: how XAML lays a layout out compared with the web's CSS (spacing, the first day's hour gutter, the clipping of short timeline items); whether a pen pressed on the selection frame grabs it rather than writing (the page switches writing off while the pointer is over it, as a safeguard); and touch (the frame's controls turn manipulation off so that a finger doesn't scroll).

Expect a round of small fixes on the first Windows build. The most likely spots:
- The `.csproj` properties for UWP on .NET 9
- `TextNudge` in `MainPage.xaml.cs`, which lines the model's text up with the ruled lines

The handwriting font is **Ink Free**, which comes with Windows 10 1803 and later. If it's missing, the app falls back to Segoe Print.
